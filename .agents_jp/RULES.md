# Mediagent 開発ルール

Mediagent はバックグラウンドで動作するメディアダウンロード daemon です。メディアの収集とダウンロードだけを担当し、メディアライブラリの管理、閲覧、共有、再投稿、ギャラリー UI の提供は行いません。

この規約は、現在の初期段階の Python プロジェクトに合わせて、軽量でありながら実行可能な内容にしています。将来、プラットフォーム対応、データベース移行、CI、デプロイ手順が成熟したら、段階的に拡張します。

## 1. 開発フロー

すべての変更は次の流れに従います。

1. 要件を理解する: 利用シナリオ、対象プラットフォーム、意図的に対象外にすることを確認します。
2. 影響範囲を確認する: 関連ファイルを読み、影響を受けるコアフロー、プラットフォームモジュール、データベース動作、設定を特定します。
3. 小さく実装する: 変更は一つの明確な目的に絞ります。
4. テストを追加する: コアフローとエラーパスにはテストが必要です。プラットフォーム統合テストをデフォルトのテスト実行条件にしてはいけません。
5. 手動で検証する: 影響を受ける CLI コマンドまたはコア関数がローカルで期待通り動くことを確認します。
6. 変更を整理する: 一時出力を削除し、認証情報やダウンロード済みメディアをコミットせず、検証方法を記録します。

## 2. 可読性の管理

- 名前は意図を表すものにします。過度な省略や、特定のプラットフォーム担当者だけが理解できる略語は避けます。
- 関数は小さく保ちます。一つの関数は一つの階層の作業だけを扱います。
- 隠れた副作用を避けます。ファイル書き込み、DB 書き込み、ネットワーク呼び出し、認証情報の読み取りを行う関数は、名前または配置でその動作が分かるようにします。
- コアフローとプラットフォーム詳細は分離します。共通パイプラインは Pixiv、X、Instagram などの固有 API 詳細に依存してはいけません。
- コメントは、明らかではない理由、制約、外部サービスの挙動を説明するために使います。コードがすでに示している内容を繰り返してはいけません。
- エラーメッセージは問題の特定に役立つ内容にしますが、token、cookie、session、完全な認証情報を含めてはいけません。
- 抽象化は、重複を減らす、プラットフォーム差異を隔離する、または外部サービスの詳細がコアフローへ漏れるのを防ぐ場合にだけ追加します。

## 3. アーキテクチャ規約

Mediagent は、メディアの発見、重複排除、ダウンロード、ファイル書き込み、状態記録を中心に構成します。プラットフォームは取得元とダウンロードの詳細を提供するだけで、daemon の主フローを制御しません。

- `src/mediagent/core/` には共通モデル、ツール契約、スケジューリング、パイプライン、ファイル配置、リトライ方針、プラットフォーム登録を置きます。
- `src/mediagent/tools/` には agent から呼び出せる collector、filter、downloader、metadata writer、データベースツールを置きます。
- `src/mediagent/platforms/<platform>/` にはプラットフォーム API、認証、解析、プラットフォーム固有の変換ロジックを置きます。
- `src/mediagent/core/db.py` または将来のデータベースモジュールは、状態保存、重複排除、ダウンロード記録、エラー記録を担当します。
- `src/mediagent/cli.py` はコマンドライン入口を担当します。プラットフォームの業務ロジックを置いてはいけません。
- `main.py` は起動入口のみです。主要なアプリケーションフローを置いてはいけません。

プラットフォームモジュールは次の境界を守ります。

- daemon loop を直接制御しない。
- 他プラットフォームのデータへ直接アクセスしない。
- グローバルなデータディレクトリを自分で決めない。
- コアのデータベース重複排除や状態記録を迂回しない。
- プラットフォーム認証情報を metadata、log、エラーメッセージへ書き込まない。

External catalog、viewer、cleanup service は CLI consumer であり、Mediagent
platform ではありません。API client、selection policy、credentials、
pagination、scheduler、service units は所有する external project に置きます。
この repo は provider-neutral CLI contract を文書化できますが、external
implementation を保持・deploy しません。`ComicInfo.xml` などの compatibility
output は file contract であり、reader への runtime coupling を認めるものではありません。

メディアモデルは少なくとも次の種類を予約します。

- `photo`
- `video`
- `audio`

最初の実装が画像または動画だけを扱う場合でも、データモデルを単一のメディア種類に固定してはいけません。

## 4. テスト規約

- コアフロー、データベース重複排除、ファイル名生成、リトライ動作には単体テストが必要です。
- テストは安定したロジックを優先してカバーします。プラットフォームのネットワーク動作は fixture、fake client、記録済みデータで隔離します。
- デフォルトのテスト実行は、実アカウント、実 cookies、実 token、外部ネットワークに依存してはいけません。
- ネットワーク、認証情報、外部サービスが必要なテストは明示的にマークし、デフォルトではスキップします。
- 各プラットフォームでは少なくとも、空結果、新規項目、重複項目、ダウンロード失敗、一部ファイル失敗をテストします。
- テストで再現できる bug を修正する場合は、先に対応するテストを追加するか、自動テストが実用的でない理由を説明します。
- テストデータに private bookmark、実 cookies、token、ユーザー ID、個人識別情報を含めてはいけません。

## 5. 権限境界

Mediagent のファイル操作とネットワーク動作は保守的にします。デフォルトで既存のユーザーデータを破壊してはいけません。

- 書き込み先は `MEDIAGENT_DATA_DIR`、設定済みデータベースパス、設定済み log パス、必要な cache に限定します。
- ユーザーが明示的なコマンドを実行し、そのコマンドに明確な確認フローがある場合を除き、既存のユーザーメディアファイルを削除してはいけません。
- アップロード、共有、再投稿、メディア閲覧・管理機能の提供を行ってはいけません。
- ブラウザデータ、system keychain、プラットフォームアカウント設定を変更してはいけません。
- 認証情報は環境変数または明示的な設定ファイルからのみ読み取ります。
- token、cookie、session、refresh token を log、metadata、テスト snapshot、エラー報告へ書き込んではいけません。
- ダウンロードパスは正規化し、プラットフォーム由来のデータによる path traversal や対象ディレクトリ外への書き込みを防ぎます。
- 外部サービスが rate limit、block、login error を返した場合は、状態を記録し、そのプラットフォームの今回の実行を停止します。無制限にリトライしてはいけません。

## 6. バージョン管理

- 各 commit は、「コアモデルを作成する」「Pixiv collector を追加する」「データベース重複排除を修正する」など、一つの目的に集中します。
- `.venv/`、ローカルデータベース、ダウンロード済みメディア、cookies、tokens、sessions、logs、一時出力をコミットしてはいけません。
- pull request の説明または commit message には、挙動の変更と検証方法を書きます。
- データベース schema を変更する場合は、migration、初期化時の互換戦略、またはプロジェクトが未リリースで schema を再構築できるという明確な説明を含めます。
- 純粋なフォーマット変更と挙動変更を混ぜないでください。ただし、フォーマット範囲が小さく、その変更に直接関係する場合は例外です。
- 明示的に依頼されていない限り、他人の変更を上書きまたは revert してはいけません。衝突は差分を理解してから解決します。
- 認証情報、ダウンロード済みデータ、プラットフォームログイン動作に関わる変更は、バージョン管理に入れる前に機密情報を追加していないか確認します。

推奨 ignore 項目:

```gitignore
.venv/
*.sqlite
*.sqlite3
*.db
*.log
downloads/
media/
cookies*.txt
*.token
*.session
```

## 7. 変更前チェックリスト

変更を提出または commit する前に確認します。

- 変更がプロジェクトの目的に合っている: 収集とダウンロードだけを行い、管理や閲覧を行わない。
- コアフロー、プラットフォームロジック、ダウンロードロジックが同じ層に混ざっていない。
- 新しいファイル書き込みは、許可された data、database、log、cache の場所だけを対象にしている。
- token、cookie、session、個人データ、実際のダウンロード済みメディアがコードやテストに含まれていない。
- 再実行しても完了済み項目を重複ダウンロードしない。
- 失敗状態が記録され、単一プラットフォームのエラーで daemon 全体がクラッシュしない。
- 妥当なテストを追加した、または自動テストが実用的でない理由を記録した。
- 影響を受けるコマンドまたはフローを手動で検証した。
