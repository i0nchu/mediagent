# Mediagent 開發流程與規範

Mediagent 是背景自動媒體下載 daemon。它只負責蒐集與下載媒體，不負責媒體庫管理、媒體瀏覽、分享、轉貼或提供相簿 UI。

這份規範刻意保持輕量但可執行，適合目前早期 Python 專案。若未來平台支援、資料庫遷移、CI 與部署流程逐漸成熟，再逐步擴充。

## 1. 開發流程

每次變更都必須依照以下循環進行：

1. 理解需求：確認使用情境、平台範圍，以及刻意不做的事情。
2. 確認影響範圍：閱讀相關檔案，找出會受影響的核心流程、平台模組、資料庫行為與設定。
3. 小步實作：每次變更只聚焦在一個明確目的。
4. 補上測試：核心流程與錯誤路徑需要測試；平台整合測試不得成為預設測試的必要條件。
5. 手動驗證：確認受影響的 CLI 命令或核心函式能在本機以預期方式執行。
6. 整理變更：移除暫存輸出，避免提交憑證或下載媒體，並記錄驗證方式。

## 2. 可讀性控制

- 命名要描述意圖，不使用過度縮寫或只有平台作者才懂的名稱。
- 函式應保持短小，單一函式只負責一個層級的工作。
- 避免隱性副作用；會寫檔、寫 DB、呼叫網路或讀憑證的函式，名稱或放置位置要清楚表達。
- 核心流程與平台細節必須分離；共用管線不應依賴 Pixiv、X、Instagram 或其他平台的特殊 API 細節。
- 註解只用來解釋非顯而易見的原因、限制或外部服務行為，不重複描述程式碼本身。
- 錯誤訊息要能幫助定位問題，但不得包含 token、cookie、session 或完整憑證內容。
- 新增抽象前，先確認它能降低重複、隔離平台差異，或防止外部服務細節污染核心流程。

## 3. 架構規範

Mediagent 的架構以發現媒體、去重、下載、寫入檔案、記錄狀態為主軸。平台只提供來源與下載細節，不控制 daemon 主流程。

- `src/mediagent/core/` 放共用模型、工具契約、排程、管線、檔案落地、重試策略與平台註冊機制。
- `src/mediagent/tools/` 放 agent 可呼叫工具，例如 collector、filter、downloader、metadata writer 與資料庫工具。
- `src/mediagent/platforms/<platform>/` 放平台 API、登入、解析與平台特定轉換邏輯。
- `src/mediagent/core/db.py` 或後續資料庫模組負責狀態保存、去重、下載紀錄與錯誤紀錄。
- `src/mediagent/cli.py` 負責命令列入口，不放平台業務邏輯。
- `main.py` 只作為啟動入口，不承載主要應用流程。

平台模組必須遵守以下邊界：

- 不直接控制 daemon loop。
- 不直接存取其他平台的資料。
- 不自行決定全域資料目錄。
- 不繞過核心資料庫去重與狀態紀錄。
- 不把平台憑證寫入 metadata、log 或錯誤訊息。

外部 catalog、瀏覽器與 cleanup service 是 CLI consumer，不是 Mediagent
platform。它們的 API client、selection policy、credentials、pagination、
scheduler 與 service units 必須留在所屬的外部專案。本 repo 可以記錄
它們呼叫的 provider-neutral CLI contract，但不得承載或部署其實作。
`ComicInfo.xml` 之類相容輸出是檔案契約，不代表可以與使用它的閱讀器建立 runtime coupling。

媒體模型至少必須保留以下媒體類型：

- `photo`
- `video`
- `audio`

即使第一版只實作圖片或影片，也不得把資料模型寫死成單一媒體類型。

## 4. 測試規範

- 核心流程、DB 去重、檔名生成、錯誤重試必須有單元測試。
- 測試要優先覆蓋穩定邏輯；平台網路行為應以 fixture、假 client 或錄製資料隔離。
- 預設測試不得依賴真實帳號、真實 cookies、真實 token 或外部網路。
- 需要網路、憑證或外部服務的測試必須明確標記，並在預設情況下跳過。
- 每個平台至少應測試：空結果、新項目、重複項目、下載失敗、部分檔案失敗。
- 修正可由測試重現的 bug 時，需先補對應測試，或說明為什麼不適合自動化測試。
- 測試資料不得包含私人收藏、真實 cookies、token、使用者 ID 或可識別的個人資訊。

## 5. 權限邊界

Mediagent 的檔案與網路行為必須保守，預設不破壞使用者既有資料。

- 只寫入 `MEDIAGENT_DATA_DIR`、指定資料庫路徑、指定 log 路徑與必要 cache。
- 不刪除使用者既有媒體檔，除非使用者執行明確命令，且該命令有清楚確認流程。
- 不上傳、不分享、不轉貼、不提供媒體瀏覽與管理功能。
- 不修改瀏覽器資料、系統 keychain 或平台帳號設定。
- 憑證只從環境變數或明確設定檔讀取。
- token、cookie、session、refresh token 不得寫入 log、metadata、測試快照或錯誤回報。
- 下載路徑必須經過正規化，避免平台資料造成路徑穿越或寫入目標目錄之外。
- 若外部服務回傳限制、封鎖或登入錯誤，程式應記錄狀態並停止該平台本輪作業，不應無限制重試。

## 6. 版本控制

- 每次 commit 聚焦單一目的，例如「建立核心模型」、「加入 Pixiv collector」、「修正 DB 去重」。
- 不提交 `.venv/`、本機資料庫、下載媒體、cookies、tokens、session、log 或暫存輸出。
- PR 描述或 commit message 需描述行為變更與驗證方式。
- 若變更資料庫 schema，需附 migration、初始化兼容策略，或清楚說明專案仍在發布前且 schema 可重建。
- 不把純格式化與行為變更混在一起，除非格式化範圍很小且與該變更直接相關。
- 不覆寫或回退他人未明確要求移除的變更；遇到衝突時先理解差異再處理。
- 任何涉及憑證、下載資料、平台登入方式的變更，都必須在進入版本控制前額外檢查敏感資訊。

建議排除項目：

```gitignore
.venv/
*.sqlite
*.sqlite3
*.db
*.log
downloads/
media/
cookies*.txt
*.token
*.session
```

## 7. 變更前檢查清單

在提交或交付變更前，確認：

- 這次變更符合專案定位：只蒐集與下載，不管理與瀏覽媒體。
- 核心流程、平台邏輯、下載邏輯沒有混在同一層。
- 新增的寫檔行為只會落在允許的資料目錄、DB、log 或 cache。
- 沒有把 token、cookie、session、個人資料或真實下載內容放進程式碼與測試資料。
- 重複執行不會重複下載已完成項目。
- 失敗狀態能被記錄，且單一平台錯誤不會讓整個 daemon 崩潰。
- 已補上合理測試，或清楚記錄為什麼不適合自動化測試。
- 已手動驗證受影響的命令或流程。
